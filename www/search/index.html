    Every published item

    • Act: How a page offers actions to an assistant.
    • AI usage preferences (IETF drafts): Two IETF working-group drafts: a vocabulary for stating how content may be used by automated systems, and a way to attach it to content.
    • API catalogue (RFC 9727): A well-known address and a link relation with which a publisher lists its APIs in one link set.
    • Ask first: How a site says what automated readers may do, and how a reader says who it is.
    • Card format: What a card of this node must hold, stated so that tasks can follow it and a check can test it.
    • Cards are written in the node's own words: The decision that each card is a few lines in this node's own words, with a link to the document it describes.
    • Check the status of a document: Compare one card with the page of the body that publishes the document, and propose the result.
    • Check a published file against its digest: Compute the digest of one file of this node and compare it with the digest the discovery file gives.
    • C2PA content credentials: A specification that binds a signed record of how a media file was made and edited to the file itself.
    • IETF working group on discovering agents (DAWN): The IETF working group chartered to specify how a client discovers public facts about AI agents.
    • Data Catalog Vocabulary (DCAT 3): A W3C vocabulary for describing catalogues of datasets and data services.
    • Digest fields (RFC 9530): HTTP fields that carry a hash of the message content or of the representation, so a receiver can check what it got.
    • Find: How a program finds what a site offers: fixed addresses, typed links and catalogues.
    • From Internet-Draft to RFC: How to read the status of an IETF document: a draft is work in progress and expires; an RFC is published and keeps its number.
    • How it works: How to read the status of a document of the IETF or the W3C.
    • HTTP message signatures (RFC 9421): A way to sign parts of an HTTP message, so a receiver can check who sent it and that it was not changed.
    • JSON canonicalization (RFC 8785): One fixed way to write JSON, so that equal data gives equal bytes before hashing or signing.
    • JSON-LD 1.1: A W3C syntax for writing linked data as JSON, so that a JSON document maps to RDF.
    • Link sets (RFC 9264): A document format that carries many typed links at once, in JSON or in text.
    • llms.txt: A Markdown file, at the root of a site or of a path in it, that gives language models a short overview and links to Markdown pages.
    • ODRL Information Model 2.2: A W3C policy language for stating how content and services may be used.
    • PROV-O: A W3C vocabulary for recording who or what made or changed a thing.
    • Publish gate
    • RDF: The W3C data model for statements about things: triples, graphs and datasets.
    • RDF dataset canonicalization: A W3C algorithm that gives one fixed form of an RDF dataset, so that it can be hashed or signed.
    • robots.txt (RFC 9309): The rules of the robots.txt file, with which a site tells crawlers what they may fetch.
    • schema.org: A shared vocabulary of types and properties for describing things on web pages.
    • security.txt (RFC 9116): A text file at a well-known address that says how to report a security problem.
    • SHACL: A W3C language for checking an RDF graph against a set of conditions called shapes.
    • SKOS: A W3C data model for thesauri, taxonomies, classification schemes and subject heading systems.
    • SPARQL: The W3C query language for RDF data, for asking questions of a graph.
    • Propose a document this node should describe: Name a published document that an agent-readable site builds on and that has no card here, with its address and status.
    • Re-check the AI usage preferences drafts: Read the current versions of the two IETF drafts and bring their card up to date, before 20 February 2027.
    • Re-check the working group on discovering agents: See whether the IETF working group has adopted a document, and bring its card up to date, before 18 February 2027.
    • Re-check the web bot authentication draft: Read the current version of the working group's draft and bring its card up to date, before 2 May 2027.
    • TDM Reservation Protocol: A way for a rights holder to reserve text and data mining rights, in a file, a header or page metadata.
    • Trust the bytes: How a reader checks that a file is the one that was published, and who vouches for it.
    • Understand: How facts are written so that programs on different sites read them the same way.
    • Upkeep: The node's own work on one board: the decision, the card format, the gate and the open tasks.
    • Verifiable Credentials Data Model 2.0: A W3C data model for signed claims that an issuer makes, a holder keeps and a verifier checks.
    • W3C reports and Recommendations: How to read the status of a W3C document: a Recommendation is a W3C standard; a Community Group Report is not.
    • Web bot authentication (IETF working group): The IETF working group on how automated clients prove who they are to the sites they visit.
    • Web linking (RFC 8288): Typed links between web resources, and the HTTP Link header field that carries them.
    • WebMCP: A draft browser interface with which a web page registers tools that an assistant in the browser can call.
    • Well-known addresses (RFC 8615): A reserved path on every site, /.well-known/, where a site publishes files about itself at a fixed place.
    • Who made it: How a claim or a media file carries a record of its origin that can be checked.
